## 三、前提检查（不过则回到阶段 7）

```
☐ 闸门已经在系统里（不靠人判断），且拦截稳定
☐ 主线标识贯穿全流程，可正查可反查
☐ 关键数据当天录入（不是月底补录）
☐ 已有"候选方案 + 人采纳"的交互先例
☐ 操作日志不可删，且能区分虚拟账号
☐ 口径库/规则库/文档库已结构化（且文档有版本）
```

> **如果第一项或第二项不过，不要上 Agent。**
> 没有闸门和主线，Agent 就只是"很聪明但没人敢用"的助手。

---

## 四、工程规范核对（九条硬规矩）

```
☐ 1  写操作一律走既有业务 API，禁止直连数据库
☐ 2  Agent 以"虚拟账号"接入，权限等同其服务的岗位，写操作全程审计
☐ 3  幂等：重试不产生重复单据
☐ 4  必须有降级路径，且永不阻塞生产
☐ 5  输出是"候选方案 + 证据"，不是结论
☐ 6  输出带数据时点（data_as_of）与来源
☐ 7  干跑（dry-run）模式：写动作先产出 diff 给人看
☐ 8  阈值护栏：金额/数量/等级变更超阈值必须人工审批
☐ 9  提示注入防护 + 工具白名单（外部文本视为不可信输入）
```

---

## 五、禁止清单（逐条确认已内建）

```
☐ 不绕过或建议绕过任何硬闸门
☐ 不修改已报工 / 已审核 / 已执行的冻结数据
☐ 不直接对外发送消息（客户 / 供应商 / 经销商）
☐ 不参与利益分配决策（工资 / 计件单价 / 罚款）
☐ 不自动批准任何质量放行（特采 / 让步接收）
☐ 数据缺失时不推测、不"补齐"事实值，必须说"缺数据"
☐ 不用自然语言生成规则判定结果（判定来自确定性代码，Agent 只做解释）
```

## 六、输出结构（统一 schema，便于评测与审计）

```yaml
agent: <agent_id>
trigger: <trigger_event>
data_as_of: <ISO8601>                 # 数据时点（硬规矩 6）
summary: <一句话结论>
candidates:                           # 候选方案（硬规矩 5），≥2 个
  - id: A
    score: <0-100>
    metrics: {}
    risks: []
  - id: B ...
evidence:                             # 证据链，每条可追溯
  - type: <rule|document|data|history>
    ref: <规则版本 / 文档编号+版本+页 / 查询时点+条件>
confidence: <low|medium|high>
limits: <本次输出的边界声明>
requires_human: true
suggested_action:                     # 干跑（硬规矩 7）
  label: <按钮文案>
  api: <既有业务 API 名>
  dry_run: true
```

## 七、四波推进计划

| 波次 | 周期 | 内容 | 权限 | 成功标准 | 实际完成 |
| --- | --- | --- | --- | --- | --- |
| 一 | W0–W6 | 只读参谋 | 只读 | 主动使用频次↑；输出带时点与引用；无事实错误 | ☐ |
| 二 | W6–W14 | 候选方案类 | 草稿 | 采纳率 ≥ ___%；采纳后结果不差于人工 | ☐ |
| 三 | W14–W26 | 闭环执行 + 主动追办 | 草稿→闭环待办 | 待办转化率；指标可量化改善 | ☐ |
| 四 | W26+ | 跨系统协同 + 效果复盘 | 受控执行 | 溯源分钟级；否决理由转化为规则调整 | ☐ |

**每波结束必产出**

```
☐ 该波 Agent 的度量数据（质量 / 采纳 / 效率 / 效果 四类）
☐ 否决理由归类报告 → 转成规则或权重调整项
☐ 下一波的前提检查
☐ 负面测试用例更新（新增本波发现的越权/编数据风险）
```
