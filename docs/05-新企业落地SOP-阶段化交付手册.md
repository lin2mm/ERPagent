# 新企业落地 SOP：从 0 到上线，再到 Agent 化的八阶段手册

> 这份手册把两个案例的交付方法，压缩成一条**可以对着干的流水线**。
> 每个阶段都有：**目标 → 动作清单 → 输出物 → 退出准则（Gate）→ 常见坑**。
> 阶段 1–4 的时间参考案例 B 的 8 周节奏；阶段 5–7 参考案例 B 的"开发完成后动态排期"。
> 阶段 8 是 Agent 化的四波推进。

---

## 总览：一条流水线

```
阶段 0  机会判断与立项              → Go / No-Go
阶段 1  现场调研与主线识别（W1）      → 企业画像 + 主线对象 + 闸门清单 + 痛点账单
阶段 2  蓝图冲刺与设计冻结（W1–W2）   → 蓝图签字 + 流程签字 + 集成接口确认
阶段 3  范围分层与对价确认（W2）      → 首版三层范围 + 后移清单 + 双方配合清单
阶段 4  并行开发与真机演示（W3–W8）   → 阶段性真机演示 + 交付测试
阶段 5  集成调试与数据迁移            → 数据可用 + 接口打通
阶段 6  分层培训与试点上线            → 三工序跑通
阶段 7  全厂推广与持续迭代            → 逐工序复制 + 模块排队上线
阶段 8  Agent 化四波                 → 只读参谋 → 候选方案 → 闭环执行 → 跨系统协同
```

**贯穿全程的四条纪律**：

1. **双周真机演示**——偏差当场暴露，不留到最后一周。
2. **两个硬检查点**（对应案例 B 的 W4、W6）——偏差超阈值立刻启动范围降级，**先保主线**。
3. **顺延的明说，不静默延期**。
4. **验收认真机不认文档**。

---

## 阶段 0 · 机会判断与立项

### 目标
在投入任何资源前，判断**这家企业现在该不该做、能做多大、从哪切入**。

### 动作清单

**0.1 判断成熟度（决定方案的形态）**

| 观察项 | L0/L1（基础簿记） | L2（规则自动化） | L3（算法优化） |
| --- | --- | --- | --- |
| 库存 | Excel / 手工台账 | 系统里的库存有流水可对账 | 有安全库存与呆滞分档策略 |
| 车间 | 纸质派工、口头报工 | 有工单系统、能报工 | 有排产/套料算法 |
| 质量 | 检验记录在纸上 | 有检验台账与放行流程 | 有缺陷定位与规避 |
| 设备 | 无采集 | 有部分计数设备 | 数据接入系统并对追溯生效 |
| 标识 | 无码或码不联通 | 有码但只在单点用 | 码贯穿全流程 |
| 决策 | 靠经验 | 有看板与报表 | 机器给候选方案 |

> **规则**：L0/L1 的企业，**先做 L2**（闸门 + 流水 + 台账）。
> 直接上 Agent 会得到一个"很聪明但没抓手"的助手——**它下面没有闸门，没人敢让它做。**

**0.2 找"已投入但没被利用的资产"**（案例 B 的抓手思路）

- 已有的打码/喷码设备 → 能不能升级成主线标识？
- 已有的地磅/计米/计数设备 → 能不能变成自动报工？
- 已有的 ERP/进销存 → 能不能当数据源与回写目标？
- 已有的图纸/工艺文件 → 能不能结构化成规则库？
- 已有的微信群/纸质单 → 能不能先搬成"可留痕的电子流程"？

**0.3 找"可解耦的两段"**（案例 B 的压缩交期思路）

把主流程画成一条时间轴，**标出每一段在等谁**。凡是有"下游不依赖上游"的部分，
都可以提前启动。**回报最高的改造项目往往不是"提效"，而是"消除等待"。**

**0.4 判断政治条件**

| 必须确认 | 不合格的信号 |
| --- | --- |
| 一把手是否愿意任项目主席并参加关键评审 | "让 IT 部门对接就行" |
| 关键用户能否在头两周投入 ≥50% 工时 | "我们业务太忙，你先调研" |
| 是否有明确的业务负责人（不是 IT） | 只有 IT 牵头 |
| 是否接受"设计冻结后走变更评估" | "我们需求随时会变" |

> **中小制造企业上系统，成败第一因素不是技术，是一把手的参与度。**
> 这一条不过，宁可不立项。

### 输出物

- **企业数字化成熟度自评表**（L0–L4）
- **痛点账单**（用客户自己的话，列出最贵的三样东西）
- **可从速切入的资产清单**
- **Go / No-Go 结论**

### Gate
`一把手同意任项目主席` 且 `关键用户工时承诺到人` 且 `成熟度自评完成`。

### 常见坑
- 把"客户说要个系统"当成需求，实际痛点可能只是某个部门的报表。
- 没有判断成熟度就直接做方案，导致方案与客户实际能力脱节。
- 忽略政治条件，做到一半关键用户不配合。

## 阶段 1 · 现场调研与主线识别（W1）

### 目标
用一周时间，回答**第 2 章那七道必答题**，并收集到足以做流程签字的事实。

### 动作清单

**1.1 走一遍现场**（必须亲眼看，不能只听汇报）

按物料流动方向走：**收货 → 入库 → 备料 → 上机 → 在制 → 检验 → 入库 → 拣货 → 发货**。
记录：**每个环节在用什么纸/什么表/什么群、谁在记、记完给谁。**

**1.2 访谈七类人**（每类 1–2 人，各 1 小时）

| 对象 | 必问 |
| --- | --- |
| 老板 | 你最关心的三个数是什么？现在多久能看到？最怕发生什么？ |
| 计划/生产部长 | 排产靠什么？插单多不多？最常缺什么？交期怎么承诺的？ |
| 车间主任/班组长 | 一天要填多少张表？哪些数据是"编"的？异常怎么上报？ |
| 一线工人 | 报工麻烦在哪？计件怎么算、什么时候能看到？最烦哪个校验？ |
| 质检 | 检验标准在哪？不合格怎么处置？出了客诉怎么查？ |
| 仓管 | 找一卷料要多久？账实差多少？盘点多久一次？ |
| 财务 | 成本什么时候算得出来？应收多久回？和业务系统对得上吗？ |

> **访谈的第一原则：问"你昨天干了什么"，不要问"你觉得系统应该有什么功能"。**

**1.3 填七道必答题**（详见 `03-通用蓝图`）

```
① 主线对象是什么？          ② 单据层级有几层？
③ 状态机怎么定义？          ④ 闸门在哪？（最重要的题）
⑤ 采集点在哪？（人报 vs 机联） ⑥ 谁看什么、在哪看？  ⑦ 边界在哪？
```

**1.4 拍现场照片**（用于后续对比"改造前"）

- 纸质单据、白板、看板、群消息、机器铭牌、条码标签。
- **这些照片是后续"改造前 vs 改造后"最有说服力的材料，也是培训素材。**

**1.5 收集主数据样本**（决定迁移可行性）

物料/客商/期初库存的导出样本、图纸/工艺文件样本、计件工序与单价表。
**案例 B 的做法：把"旧系统能不能导出明细"列为第一周必须验证的事项——导不出就降级为只迁汇总余额，
历史追溯范围要书面确认接受。**

### 输出物

- **企业画像一页纸**（业务模式、主线对象、工序链、组织与岗位）
- **现状流程时间轴**（标出所有"等待"）
- **七道必答题的初稿**
- **闸门候选清单**
- **主数据质量评估**（能不能迁、缺哪些）

### Gate
`七道必答题有答案` 且 `闸门候选清单已形成` 且 `主线对象已在现场验证过（能举例说明一卷/一件怎么流）`。

### 常见坑
- 只访谈管理层，不看一线 → 报工粒度、界面约束会设计错。
- 把"现状是 Excel"当成"需要把 Excel 搬到网上"，而没看流程本身能不能优化。
- 没有在第一周确认设备协议和旧系统导出能力 → 后面必然延期（案例 B 明确列为风险项）。

## 阶段 2 · 蓝图冲刺与设计冻结（W1–W2）

### 目标
让**关键用户坐下来把流程逐条过、逐条签**，并在第二周**冻结设计**。

### 动作清单

**2.1 蓝图冲刺会议（1–3 天，分业务线开）**

案例 B 的做法：把客户分成**四条业务线**（销售 / 技术 / 车间 / 仓库）分别开会，
**逐条过流程、逐条签**。每场会产出两样东西：

1. **流程确认表**（谁在什么条件下做什么，输出什么单据）
2. **闸门确认表**（哪些校验必须硬拦、拦了以后怎么办）

**2.2 画"一单一流程"的主流程图**

**不要画泳道图的八股文**，画**一张真实订单从头到尾的时间轴**，标出：
谁做、在哪个页面/终端做、触发什么状态变化、有没有校验、卡住了走什么分支。

**2.3 定义状态机与字典**

```
① 主线对象的完整状态枚举（带数值编码）
② 每个状态的进入条件（由哪个动作触发）
③ 可逆性（哪些能撤销/恢复）
④ 终态（越少越好）
⑤ 事件类型清单（用于事件档案）
⑥ 单据状态链（草稿→审批→执行→关闭…）
⑦ 枚举字典（等级、优先级、告警级别、连接方式…）
```

> **这份字典后续同时是：开发文档、测试用例来源、和操作手册的附录。**
> 案例 A 把它做成了"附录 B 状态字典速查表"，一条不漏。

**2.4 定义闸门（逐条与客户确认）**

对每道闸门确认五件事：

| 确认项 | 示例 |
| --- | --- |
| 规则 | 客户等级决定可发物料等级（VIP 仅可发 A 级） |
| 拦截方式 | 硬拦 / 软警告二次确认 / 提醒 |
| 出路 | 走特采审批并留档 |
| 谁有权放行 | 质量负责人 + 总经理（超阈值） |
| 留痕 | 发货记录保留等级快照 |

> **把闸门做成表格让客户签字，是保护双方的最有效手段。**
> 上线后有人说"这拦得太死了"，翻出这张表就行。

**2.5 定义终端与角色矩阵**

```
① 场景列表 → 决定有几个终端（PC / 工位机 / PDA / 大屏 / 驾驶舱 / 小程序 / 门户）
② 角色列表（含外部单位）
③ 角色 × 菜单矩阵（可操作 / 只读 / 不可见 / 限定说明）
④ 数据范围隔离规则（组织/厂区隔离、集团穿透需授权、外部单位只看自己）
⑤ 每个角色的登录落点
```

> **案例 B 的做法值得直接抄：把这张矩阵图发给各部门负责人，请他们对照自己的岗位逐一核对。**
> 这是把它们变成"共同承诺"而不是"乙方交付物"的关键一步。

**2.6 确认集成接口（第一周必须启动）**

- 设备：品牌、型号、**通信协议**、厂商联系方式、能否配合联调；
- 既有系统：数据能导出哪些字段、有无 OpenApi、能否回写；
- 外部平台：用企业微信还是钉钉、短信、电子签。

> **案例 B 明确：打标机的品牌/型号/协议第一周确认，厂商配合联调——"
> 这条不通，打码主线直接受冲击"。并对老设备对接预留 15%~20% 缓冲，专职工程师第一周就上。**

**2.7 设计冻结（W2 末）**

冻结的对象：**流程、状态机、闸门、权限矩阵、接口清单**。
冻结之后：**新需求不再口头往里塞，走正式变更评估。**

> **"这是两个月守得住的第一条纪律。"**

### 输出物

- 主流程图（一张真实订单的时间轴）
- **状态机与字典 v1.0**
- **闸门清单（客户签字）**
- **角色 × 终端 × 菜单矩阵（各部门核对签字）**
- 集成接口清单（含协议与责任人）
- 数据迁移范围与降级方案
- **设计冻结确认书**

### Gate
`四条业务线流程签字完成` 且 `闸门清单签字` 且 `权限矩阵各部门核对完成` 且 `设备协议确认`。

### 常见坑
- 蓝图会开成"需求收集会"，进来一堆新想法，把工期吃掉。
- 只签总表不签细节，后面争议不断。
- 没有客户方业务负责人签字，只有 IT 签字 → 上线后业务不认账。
- 设备协议拖到第三周才确认 → 开发无法并行。

## 阶段 3 · 范围分层与对价确认（W2）

### 目标
把"要做的东西"分成能守住和可以后移的两堆，并把激进工期变成**双边对价**。

### 动作清单

**3.1 三层范围切分**（照抄案例 B 的模型）

| 层级 | 判断标准 | 内容示例 |
| --- | --- | --- |
| **核心主线（全量交付）** | 缺了就跑不完一条单 | 系统管理、工作台、基础数据、订单、拆单/图纸、**生产执行全套**（打码、报工、防错、计件、返工、冲突裁决）、检验、仓储、**追溯中心**、工位机与 PDA |
| **高价值（并行交付）** | 显著提升但可稍后 | 客户/量尺/报价、设计任务最小版、项目台账、排产与齐套、采购委外、发货安装、报表首批、小程序审批、**审批流设计器**、车间大屏 |
| **裁剪版** | 先上一个最小可用形态 | 财务先上**收款计划+应收台账**；集团管控先上**跨厂只读看板** |

**3.2 明确后移清单并附理由**

案例 B 的示范（直接可套）：

| 后移模块 | 理由 |
| --- | --- |
| 业财全套（凭证、总账、成本、税务） | **开发密度最大、出错直接连着税务**，硬压必然砸质量 |
| 外部门户 | 要牵着外部单位的**账号、培训和意愿**走，不确定性最高 |
| 三维预览、参数化下料引擎等 | 价值需要更长的消化期 |

**并声明：后移不等于不做，首版里数据接口和菜单位都留好了，迭代直接生长，不推倒重来。**

> **"这份后移清单需要在会上得到认可，它就是工期承诺的对价。"**

**3.3 撰写双方配合清单**

**企业方（每项必须有责任人 + 时点）**：

1. 关键用户头两周投入不低于 50% 工时，**流程签字一周内完成**；
2. 主数据（物料/客商/期初库存）在第 N 周前清洗完；**计件单价第 N 周前定稿**；
3. 设备品牌型号协议第一周确认，厂商配合联调；
4. 旧系统导出能力第一周验证，导不出就降级并**书面确认接受**；
5. 培训期与试点期把工人组织到位；
6. **设计冻结之后认变更纪律**。

**方案方**：

1. 开发线满编并保持主力稳定；
2. 老设备对接预留 15%~20% 缓冲，专职工程师第一周就上；
3. **每逢双周真机演示**；
4. **两个硬检查点**（W4、W6），偏差超阈值启动范围降级；
5. **先保主线，顺延的明说，不静默延期**。

**3.4 组织项目治理**

- **项目指导委员会**：**一把手任主席**，业务负责人 + 乙方项目经理 + 关键用户代表；
- **关键用户清单连同投入比例写进项目章程**；
- 例会节奏：周会（进度/风险）+ 双周演示（成果）+ 硬检查点（决策）。

### 输出物

- 首版范围三层清单
- **后移清单 + 理由（客户会议认可）**
- **双方配合清单（每项定责任人）**
- 项目章程（含指导委员会、关键用户与投入比例）

### Gate
`后移清单客户认可` 且 `双方配合清单每项有责任人与时点` 且 `一把手任项目主席并写入章程`。

### 常见坑
- 不敢明确后移清单 → 首版范围无限膨胀 → 必然延期且质量差。
- 配合清单只写"希望贵司重视"这类空话 → **必须是可验证的动词 + 责任人 + 时点**。
- 没有把变更纪律写进对价 → 冻结形同虚设。

## 阶段 4 · 并行开发与真机演示（W3–W8）

### 目标
用**高频真机演示**替代"最后一周集中联调"，把风险前置。

### 动作清单

**4.1 五条开发线并行**（参考案例 B 的拆分）

```
线 1：平台能力（权限 / 审批流 / 消息 / 编码 / 审计）
线 2：主数据与订单（客户 / 物料 / 订单 / 配置 / 报价）
线 3：计划与排产（计划 / 工单 / 派工 / 齐套 / 缺料 / 算法）
线 4：车间执行（打码 / 报工 / 防错 / 计件 / 返工 / 工位端 / PDA）
线 5：质量 / 仓储 / 追溯 / 看板 / 集成
```

**4.2 双周真机演示（雷打不动）**

| 时点 | 演示内容 | 目的 |
| --- | --- | --- |
| **W4 末** | **端到端真机演示**：下单 → 打码 → 报工 → 追溯 | 验证主线是否连通 |
| **W6 末** | **全功能真机演示** | 验证范围是否完整 |
| **W8 末** | 交付测试 + **全功能真机演示收口** | 验收 |

**演示必须用真机、真数据、真设备，不能用 PPT 或 Mock。**

**4.3 两个硬检查点**

W4、W6 结束时评估：
- 已完成功能点 vs 计划；
- 阻塞项（接口、数据、决策）数量；
- **偏差是否超阈值 → 启动范围降级：先保核心主线，顺延项明确列出。**

> **"顺延的明说，不静默延期。"** 这句话是整个交付方法里最值钱的一句。

**4.4 每双周同步"演示记录"给客户**

每次演示写一页记录：演示了什么、客户确认了什么、发现了什么问题、下一周期要解决什么。
**这就是进度证据链，也是上线后纠纷的解药。**

### 输出物

- 可运行的阶段性系统
- 每双周的真机演示记录（客户签字或邮件确认）
- 硬检查点评估报告与范围降级决议
- 交付测试报告

### Gate
`W8 全功能真机演示通过` —— 通过的标准见阶段 4.5。

**4.5 开发完成时的验收清单**（照抄案例 B 的"不认文档，认真机"）

```
① 新建一张订单，从配置/录单、拆单/计划、下料清单、打码、报工、检验、
   入库到扫码出库，全流程在系统里走完
② 随便扫一个主线标识（卷号/部件码），3 秒调出全生命周期档案
③ 负面测试 A：让"前置条件未确认"的工序试批量报工 → 看系统拦不拦
   （案例 A 对应"首件/开工判定"；案例 B 对应"首件未确认不许批量报工"）
④ 负面测试 B：让"不满足齐套/等级"的订单试发货 → 看闸门拦不拦
⑤ 负面测试 C：让"产能超限"的产线再派一单 → 看是否硬拦截
⑥ 全部角色逐个登录，核对各自工作台与菜单是否与权限矩阵一致
```

> **注意 ③④⑤ 测的是"拦不拦得住"——这三条比任何"功能清单打勾"都更能证明系统真的能用。**

### 常见坑
- 用"完成度百分比"汇报，而不是真机演示 → 问题在最后一周集中爆炸。
- 演示用 Mock 数据 → 上线后真实数据下的性能与边界问题才暴露。
- 硬检查点不执行范围降级 → 越拖越补不上，最后靠加班砸质量。

## 阶段 5 · 集成调试与数据迁移

> 案例 B 的口径：**"开发完成后进入上线阶段，按周滚动排期，不预埋拍脑袋的日期。"**

### 目标
让系统在真实数据与真实设备下跑起来。

### 动作清单

**5.1 集成调试**

| 对象 | 检查项 |
| --- | --- |
| 设备 | 全部协议连通、心跳正常、计数准确、容差校验生效、异常离线告警 |
| 既有系统 | 出站队列连通、字段映射正确、**重试/退避/死信可重推**、对账能跑出差异 |
| 外部平台 | 小程序/企业微信/钉钉授权、消息可达、电子签可用 |

**同步机制的验收参数**（抄案例 A）：

```
事件驱动出站队列 + 15 秒轮询 + 失败指数退避最多 5 次 + 死信可人工重推
+ 每日凌晨自动对账（按业务口径比对差异）+ 字段映射全配置化
+ 双通道（OpenApi 网关优先 / 数据库中间表兜底）+ 手动拉取兜底
```

**5.2 数据迁移（三步走）**

1. **清洗**（客户负责，必须定截止日）：物料、客商、期初库存、工艺/物料绑定、单价。
2. **试迁 + 核对**：迁移后**必须与客户的账逐项核对**（数量、金额、批次），签字确认基线。
3. **降级预案**：历史明细导不出 → 只迁汇总余额，**历史追溯范围书面确认接受**。

**5.3 上线前的"数据基线冻结"**

迁移完成后立即冻结一份**期初基线快照**，后续所有差异都与之对比。
**没有基线，上线后的账实差异永远说不清是谁的问题。**

### 输出物

- 集成调试报告（设备/系统/平台逐项签字）
- 数据迁移核对表（客户签字）
- 期初基线快照

### Gate
`设备计数与系统记录误差在约定容差内` 且 `与既有系统的对账无未解释差异` 且 `期初基线客户签字`。

### 常见坑
- 数据迁移交给乙方全包 → 客户对数据没有归属感，上线后不认账。
- 没有基线快照 → 上线后账实不符无法归因。
- 集成调试不留缓冲（案例 B 要求**老设备对接预留 15%~20%**）。

## 阶段 6 · 分层培训与试点上线

### 目标
**先在能覆盖全部关键机制的三道工序上跑通**，再谈全厂。

### 动作清单

**6.1 三层培训**（案例 B 的分层）

| 层级 | 对象 | 形式 | 内容 |
| --- | --- | --- | --- |
| 管理层 | 老板 + 部门负责人 | 看板解读，2 场 | 看什么、怎么用数据开会、口径说明 |
| 关键用户 | 各业务线骨干 | 全程 3 天 + 考核 | 全流程操作 + 异常处理 + 能当内部教练 |
| 一线工人 | 按工位分小班 | **按工位小班教学** | 只教自己那一屏的几个动作 |

> **一线培训的原则：只教他那一屏。**
> 老师教太多会让人恐惧，也会让界面上的无关信息变成干扰。
> 案例 A 的工位端就是"一屏一任务、四大按钮、10 秒内完成"。

**6.2 选试点工序——标准是"覆盖关键机制"，不是"最简单"**

案例 B 的选择逻辑（**直接可套**）：

| 试点工序 | 覆盖的关键机制 |
| --- | --- |
| 工序 1（起点工序） | **标识的起点**（打码/生成主线对象） |
| 工序 2（有工艺参数的工序） | **数采验证**（温度/压力/时间等参数接入） |
| 工序 3（最复杂的工序） | **风险最高机制的验证**（托盘闭环、转码、批量报工） |

**"三道跑通，其余工序的推广就是复制。"**

**6.3 上线首月驻场**

实施团队驻场巡回，按周滚动调整。**这一段的周期不拍脑袋**，每周按实际进度和现场问题定。

**6.4 上线首月的三个必看指标**

```
① 数据及时性：报工/入库是否当天录（不是"月底补录"）
② 闸门命中率：闸门拦截的次数与原因分布（拦截多说明规则生效，也说明培训要跟上）
③ 一线使用率：工位端/PDK 的日活与单次操作耗时
```

> **如果第一周就出现"月底补录"，说明界面或报工粒度有问题，必须立刻改，不能拖。**

### 输出物

- 分层培训记录与考核结果
- 试点工序上线报告
- 上线首月周报（含三项指标）

### Gate
`三道试点工序连续两周数据完整、及时、可对账` 且 `一线使用率达标`。

### 常见坑
- 试点选最简单的工序 → 最复杂的机制没验证，全厂推广时爆炸。
- 一线培训一次性灌完 → 记不住、抵触高。
- 上线初期不驻场 → 小问题演变成"这系统不好用"的集体认知。

## 阶段 7 · 全厂推广与持续迭代

### 目标
**逐工序复制**，并按价值排队上线后移模块。

### 动作清单

**7.1 逐工序推广**

每一道新工序推广时，复用试点工序的四个模板：**操作卡、异常处理卡、培训包、上线检查表**。

**7.2 后移模块按价值排队**（案例 B 的排法）

| 批次 | 内容 | 理由 |
| --- | --- | --- |
| 第一批 | **业财全套 + 客户门户** | 财务记得准、客户体验 |
| 第二批 | **专项采购 + 套料余料** | 交期和材料成本 |
| 第三批 | 三维/增强现实等 | 营销差异化 |

**7.3 建立"数据治理常态化"**

- 每周核对一次关键字段完整率（必填项、主数据、批次）；
- 每月看一次闸门拦截原因分布（拦截原因变化 = 业务在变）；
- 每季度复核一次权限矩阵（**人员转岗、离职及时调整**；案例 A 要求"离职时停用账号但保留历史操作审计"）。

**7.4 一线反馈闭环**

设立一个**"最烦的一件事"收集渠道**（可以就是系统里的"异常上报"多一个类型）。
**收集到的每一条都要有回复**，改不了的说明原因。
——**这是把"推系统"变成"一起改系统"的唯一办法。**

### 输出物

- 全工序推广计划与完成报告
- 后移模块迭代路线图
- 数据治理例行清单

### Gate
`全部工序上线` 且 `业务可自主操作与配置（不依赖乙方驻场）`。

## 阶段 8 · Agent 化四波推进

> 详细设计见 `04-Agent工作流设计-能力地图与工程规范.md`。这里只给**执行节奏**。

### 前提检查（不过则回到阶段 7）

- [ ] **闸门已经在系统里**（不靠人判断），且拦截稳定；
- [ ] **主线标识贯穿全流程**，可正查可反查；
- [ ] **关键数据当天录入**（不是月底补录）；
- [ ] **已有"候选方案 + 人采纳"的交互先例**（如排产/拼板）；
- [ ] **操作日志不可删**，且能区分虚拟账号。

### 四波节奏

| 波次 | 周 | 内容 | 权限等级 | 成功标准 |
| --- | --- | --- | --- | --- |
| **第一波** | 0–6 | 经营日报参谋 · 工艺/SOP 问答（带引用）· 缺料追办（只出清单） | **只读** | 用户主动使用频次 ↑；**输出带数据时点与引用**；无事实错误 |
| **第二波** | 6–14 | 排产参谋 · 异常处置参谋 · 插单影响评估 · 缺陷规避改裁 · 让步放行预审 | 写**草稿** | **采纳率 ≥ 40%**；采纳后结果不差于人工 |
| **第三波** | 14–26 | 呆滞消化 · 设备预警维保 · 收款催办 · 报价参谋 · 交期承诺 | 草稿 → 闭环待办 | 待办转化率；指标改善可量化 |
| **第四波** | 26+ | 质量事故溯源 · 跨 Agent 协同 · 效果复盘反哺权重 | 受控执行 | 溯源分钟级；否决理由转化为规则/权重调整 |

### 每一波结束要产出

```
① 该波 Agent 的度量数据（质量/采纳/效果/信任 四类）
② 否决理由归类报告 → 转成规则或权重调整项
③ 下一波的前提检查
④ 负面测试用例的更新（新增本波发现的越权/编数据风险）
```

### 常见坑
- 跳过只读波次直接做闭环 → 用户没建立信任，闭环无人敢用。
- 没有"降级路径" → Agent 故障时业务停摆（违反案例 A 的"不阻塞生产"原则）。
- 让 Agent 到"能改数据"的权限 → 审计和闸门全部失效。
- 不记录否决理由 → 失去了最有价值的迭代信号。

## 附录 · 项目全程的角色与责任

| **乙方开发线负责人 ×5** | 方案方 | 五条并行线，主力稳定不中途换人 |

## 附录 · 全程"必做/必不做"速查

| 必做 | 必不做 |
| --- | --- |
| 双周真机演示 | 用完成度百分比汇报 |
| 硬检查点触发范围降级 | 静默延期 |
| 闸门清单客户签字 | 上线后再讨论"该不该拦" |
| 后移清单当场认可 | 首版范围无限膨胀 |
| 双方配合清单定到责任人 | 写"希望贵司重视" |
| 先在覆盖关键机制的工序试点 | 拿最简单的工序试点 |
| 验收测"拦不拦得住"（负面测试） | 用功能清单打勾验收 |
| 数据迁移后冻结期初基线 | 上线后才发现账实不符 |
| Agent 先只读、再草稿、再闭环 | 一步到位给写权限 |
| Agent 输出带数据时点与证据 | 只给一个结论 |
