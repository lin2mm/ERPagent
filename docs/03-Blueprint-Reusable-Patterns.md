# 通用蓝图：从两个案例提炼的可复用模式

> 把两个不同行业（**卷材辊涂/裁片** 与 **非标定制门**）的方案放在一起，去掉行业词汇，
> 剩下的就是一套可以直接搬到第三家、第四家企业的**通用蓝图**。

---

## 1. 两个案例的同构性

| 维度 | 案例 A（卷材） | 案例 B（非标门） | 抽象出的通用件 |
| --- | --- | --- | --- |
| **主线对象** | **卷号**（一卷多单、一单多卷） | **部件码**（一樘门一生不变） | **一个主线标识**承载全部追溯 |
| **状态机** | 卷料 17 态 | 部件码 + 工序进度状态 | **带终态的单向状态机 + 事件档案** |
| **派生 / 重组** | 合卷、倒卷 → `-M{n}` / `-S{n}` | 转码、补码 → 谱系保留 | **对象可以分裂/合并，但谱系不能断** |
| **硬闸门** | 等级匹配、防多产、产能 100% 拦截 | 齐套校验、首件未确认不许批量报工 | **物理/合规性闸门，无人可绕** |
| **软约束算法** | 自动排单（5 权重）、拼板（8 硬约束） | 排产板 + 齐套约束 + 缺料分析 | **算法出候选，人来定** |
| **采集点** | 机联（5 种协议）+ 人工报工 + 容差校验 | 扫码 + 数采（温度/压力/温湿度）+ 计件 | **能自动就自动，人工修正要留原因** |
| **离线兜底** | 工位端离线队列（幂等）、PWA IndexedDB | 车间边缘节点（本地出码/防错/看图） | **车间动作不依赖云端实时** |
| **冲突裁决** | 先到先得 + 人工确认 | 裁决队列 + 班组长在线裁决 + 两侧证据 | **冲突是可预期的，不是异常** |
| **权限模型** | 9 角色 × 菜单 + 终端落点 | 13 角色 × 18 菜单 + 组织隔离 + 外部门户 | **角色 × 终端 × 菜单三级矩阵** |
| **多端** | 5 端 + 统一登录 | 8 入口，一个账号 | **按场景切终端，不按角色切** |
| **看板分层** | 工位看板 / 车间大屏 / 会议看板 / 驾驶舱 | 车间大屏 / 移动看板 / 跨厂只读看板 | **四层看板：执行/现场/例会/决策** |
| **ERP 边界** | 出站队列 / 退避 / 死信 / 对账 / 凭证导出 | 与现有进销存/财务的迁移与并存 | **一张边界表 + 一套可靠同步机制** |
| **交付节奏** | —— | 8 周纯开发 + 双周真机演示 + 硬检查点 | **短周期 + 高频真机验证 + 明确对价** |
| **验收方式** | 操作手册 + 状态字典 + 权限矩阵 | 负面测试 + 逐角色核对 | **验收测"拦不拦得住"，不测"功能有没有"** |

**结论**：两家企业在业务上毫无关系，但**系统骨架几乎一致**。
这说明存在一套**行业中立的"制造企业数字化内核"**，行业差异只体现在三处：
**① 主线对象是什么；② 闸门规则是什么；③ 算法约束是什么。**

## 2. 制造企业数字化的七道必答题

给任何一家新企业做方案，把下面七个问题问完、答完、让客户签字，方案就成型了。
**答不上来的题，就是项目的风险点。**

### 第 1 题：你的**主线对象**是什么？

主线对象 = 贯穿全流程、唯一标识、可以被追溯的那一个东西。

| 类型 | 典型行业 | 主线对象 | 判别特征 |
| --- | --- | --- | --- |
| 卷/料型 | 钢卷、薄膜、纸张、布匹、线缆 | **卷号** | 按长度/重量计量；一卷可服务多单、一单可消耗多卷；有**余料**概念 |
| 单件型 | 门、窗、家具、模具、非标设备 | **件/部件码** | 一物一码；一生不变；有**转码/补码**需求 |
| 批次型 | 食品、化工、医药、涂装 | **批次号/托盘码** | 按批投料；批次决定质量属性；有**保质期/效期** |
| 项目型 | 工程、成套设备、幕墙 | **项目号/楼栋号** | 按项目交付；多层级 BOM；有**齐套**约束 |
| 工序型 | 机加工、注塑、表面处理 | **工单号** | 车间是离散工位；瓶颈在排产和换型 |

> **一个企业可能有 2~3 个主线对象并存**（如案例 B：部件码为主，托盘码/批次码/箱码为辅）。
> **主辅要分清楚**——主对象决定状态机归谁，辅对象只做归集。

**判别口诀**：**"客户是按什么付钱的，主线对象就是什么之后的那一层。"**
客户按"片"买但按"卷"生产 → 主线是卷（案例 A）；
客户按"樘"买但按"块板"生产 → 主线是部件码（案例 B）。

### 第 2 题：**单据层级**有几层？

抄这个五层结构，绝大多数制造业都适用：

```
客户需求层   │ 销售订单 / 合同 / 项目          回答"客户要什么、要多少、何时交"
规划层       │ 生产计划 / 主计划 / 项目计划      回答"做什么、做多少、用哪类料"
执行层       │ 工单（制造令）/ 作业单           回答"具体怎么做、用哪些料"
派工层       │ 派工单 / 排程 / 班次任务         回答"派给谁、哪条线、什么顺序、哪天做"
记录层       │ 报工 / 检验 / 出入库 / 事件      回答"做了多少、消耗多少、何时做的"
```

**三条硬性要求**：
1. **每一层必须有唯一编号规则**（案例 A 的 `SO- / PP- / WO-日期-序号 / D日期-序号`）。
2. **上下层必须能双向穿透**（点订单看工单，点工单看订单）。
3. **层与层之间要有依赖/拆合规则**（案例 A 的"裁片计划依赖辊涂计划"；一单多卷、一卷多单）。

### 第 3 题：**状态机**怎么定义？

**模板（照抄即可）**：

```
[初始态] → [中间态 1] → [中间态 2] → ... → [终态]
                    ↘ [异常态] → [处置态] → 回到主线 / 终态
```

**四要素**：

| 要素 | 说明 | 案例参考 |
| --- | --- | --- |
| **枚举值** | 用整数编码，字典化，写进附录速查表 | 卷料 `0..16` |
| **进入条件** | 每个状态由哪个业务动作触发 | "报工后自动进入辊涂中" |
| **可逆性** | 哪些能回退（撤销/恢复），哪些不能 | 工单"已撤销 ⇄ 已恢复"；卷"已退货可恢复" |
| **终态** | 终态必须少（案例 A 只有 已发货/已报废/已退货 三个） | 终态越多，数据越脏 |

**两个必配机制**：
- **事件档案**：每次状态迁移记一条事件（谁、何时、为什么），可扫码还原全过程。
- **谱系（闭包表）**：对象分裂/合并后，老标识自动重定向到新标识。

> **状态机设计得好不好，判断标准是：车间里任何一个人，拿起任何一个主线对象，
> 扫一下就知道它现在能干什么、不能干什么。**

### 第 4 题：**闸门在哪？**（最重要的题）

闸门 = **不通过就绝对过不去的硬校验**。它是"系统"和"电子表格"的分水岭。

**闸门的四种类型**：

| 类型 | 特征 | 案例 | 争议度 |
| --- | --- | --- | --- |
| **物理不可能** | 客观做不到，不用解释 | 产能 100% 拦截、在途卷未到厂不能派工 | **最低** ★优先做 |
| **合规/认证** | 外部规则强制要求 | 防火门强制校验防火五金认证；等级匹配发货 | 低 |
| **质量/工艺** | 技术上做得到但会产生不良 | 首件未确认不许批量报工；换卷须同宽度同膜系 | 中 |
| **管理规则** | 内控要求，会得罪人 | 超信用额度不下单；8 月订单不能派到 7 月执行 | **最高**，需要老板背书 |

**闸门的设计规范**：

1. **拦截必须给出原因和出路**。"等级校验不通过"不够，要说"该客户为 VIP，仅可发 A 级物料；
   如需发货请走特采审批"。
2. **闸门要能"走流程绕过"**，不能是死墙。案例 A/B 的做法：特采审批 / 让步放行 / 更高权限审批，
   **但留档**。
3. **闸门触发的拦截要有视觉与听觉反馈**——红屏 + 语音告警（案例 A 的换卷扫错）。
4. **先做"物理不可能"和"合规"两类**，管理规则闸门要老板签字后再上。
5. **每上线一道闸门，都要问一句："有没有人会因此没法干活？"** 如果有，先给出路再上闸门。

> **一场上线谈话里，老板问"这系统能管住什么"，答案应该就是闸门清单。**

### 第 5 题：**采集点在哪？**（人报 vs 机联）

**采集设计三原则**：

**① 报工粒度必须匹配工序的物理形态。**
- 单件工序 → 单件扫码（裁板）；
- 连续/批量工序 → 整托/整批一枪（喷涂线整托报工）。
- **"不逼工人逐件点"** —— 这是决定一线是否抵触的关键细节。

**② 能自动就自动，人工修正必须留原因。**
案例 A 的三态模型可以直接抄：

| 来源 | 编码 | 规则 |
| --- | --- | --- |
| 手工录入 | `Manual` | 无设备时使用 |
| 机联自动 | `Auto` | 以设备计数为准 |
| 机联 + 人工修正 | `AutoModified` | **必须填写修正原因**；超容差弹二次确认 |

**容差机制**：报工数量与机联计数偏差超过配置的容差百分比 → 弹出二次确认框，
显示偏差百分比与合计 → 确认后才提交。**软警告，不是硬拦截**
（因为设备本身也会漂移，硬拦会瘫痪生产）。

**③ 采集的数据要挂得住追溯。**
案例 B 的做法值得抄：**工艺参数（温度/压力/时间/温湿度）跟着主线标识挂进档案**。
"不光知道谁做的，还知道当时机器是什么参数。"

**设备接入的通用清单**（案例 A 已验证）：

| 项 | 可选项 |
| --- | --- |
| 设备类型 | 编码器 / IO 模块 / PLC / 视觉检测 / 称重 / 仪表 |
| 连接方式 | `OpcUa` / `ModbusTcp` / `Mqtt` / `HttpPush` / `DbPoll` |
| 监控项 | 实时计数 / 心跳时间 / 在线离线状态 |
| 配置项 | 计数类型（计米/计片/计重）、报工容差、停用启用 |

### 第 6 题：**谁看什么、在哪看？**

**三维矩阵**：`角色 × 终端 × 菜单`。

**终端按场景切，不按角色切**（两个案例一致）：

| 终端 | 场景 | 硬性设计约束 |
| --- | --- | --- |
| PC 管理端 | 办公室深度操作 | 左侧菜单 + 全局搜索 + 面包屑 |
| 工位机/平板 | 车间一线作业 | 大按钮、一屏一动作、**长按防误触**（戴手套） |
| PDA/手机 | 走动场景（仓库/质检/安装） | 扫码优先、离线队列 |
| 大屏 | 现场可视化 | **免登录**、零按钮、自保护（Kiosk）、扫码定位 |
| 驾驶舱 | 决策 | **强制只读**、后端统一口径、前端零加工 |
| 门户 | 外部单位 | 动态水印、下载授权、结算关闭即收权 |

**菜单的可见性三态**（案例 B 的图例做得最清晰）：
`可操作 / 只读 / 不可见`，再加一个 **`限定说明`**（同一菜单不同角色的可见粒度不同）。

**菜单排序 = 生意顺序**（案例 B）：
`销售 → 订单 → 设计 → 技术 → 计划 → 采购 → 生产 → 质量 → 仓储 → 交付 → 财务`。
**让新员工看菜单就能看懂生意全貌。**

**登录落点 = 岗位工作现场**：生产部长→计划编排中心、老板→驾驶舱、工人→工位平板。
**再加"我的待办 + 异常计数 + 快捷入口"**，把"找功能"变成"点待办"。

### 第 7 题：**边界在哪？**

**必须画两张边界表**：

**① 与既有系统的边界表**（案例 A 的写法，逐行填并签字）：

| 业务对象 | 本系统 → 外部系统 | 外部系统 → 本系统 |
| --- | --- | --- |
| 销售订单 | — | 订单行同步 |
| 生产入库/领退料 | 单据回写 | — |
| 发货 | 销售出库回写 | — |
| 财务 | 凭证按月导出 | 总账、发票、税务保留在外部系统 |
| 采购 | — | 采购订单拉取/同步 |

**② 与人的边界表**（这个常被忽略）：
哪些事系统只**记录**不**决定**？案例 B 给了一个漂亮的例子：
**"月末系统出计件汇总对账单，班组公示后导出供薪酬发放——系统不碰发工资，但明细、勾稽、稽核全备。"**

> **划清边界的标准：凡是会引起强对抗的决策（发多少钱、罚不罚），系统只提供依据，不做决定。**

**同步机制的可靠性要求**（直接抄案例 A 的参数）：

```
事件驱动出站队列（15 秒轮询）
  + 失败指数退避（最多 5 次）
  + 死信可人工重推
  + 每日凌晨自动对账（按业务口径比对差异）
  + 字段映射全配置化（对方列名变化无需改代码）
  + 双通道接入（OpenApi 网关优先 / 数据库中间表兜底）
  + 手动拉取作为兜底手段
```

## 3. 智能化成熟度阶梯（L0→L4）

**"智能化"不是一个开关，是五个台阶。** 给企业做升级时，必须明确告诉客户"你现在在哪一级、这次上到哪一级"。

| 级别 | 名称 | 特征 | 案例中的体现 |
| --- | --- | --- | --- |
| **L0** | 纸/Excel | 手工台账，事后统计 | 改造前的现状 |
| **L1** | **记录数字化** | 单据上系统，能查能统计 | 出入库流水、检验台账、变更日志 |
| **L2** | **规则自动化** | 校验、联动、自动核销 | 自动倒扣、自动核销订单、去重、等级校验、齐套校验、库存预警 |
| **L3** | **算法优化** | 求解/推荐，输出候选方案 | 自动排单（加权）、拼板套料（8 硬约束）、缺料分析、呆滞分档 |
| **L4** | **智能体协同（Agent）** | 主动感知→推理→提议→（受控）执行→复盘 | 两个案例**都还没到**，是留给下一步的空间 |

> **重要判断**：两个案例都已经扎实做到 L3，且**每一步都给自己留了"人拍板"的位置**。
> 这就是为什么它们的 Agent 化路径会很顺——**L4 不是推倒重来，是在 L2/L3 之上加一层"主动的调用者"。**
>
> 如果一家企业还在 L0/L1，**不要直接卖 L4**。先把 L2 的闸门和自动联动做出来，
> 因为 **Agent 需要一个"确定的、有护栏的执行环境"才能安全落地**。

## 4. 可复用资产库（做新项目时的"半成品仓库"）

案例 B 之所以敢承诺两个月，靠的是这句话：

> **"这套系统有现成的产品化基线：权限、审批流、消息、编码引擎这些平台能力是现成的，
> 行业里的拆单、齐套、计件逻辑也已沉淀在行业包里，五条开发线并行推进。"**

**分解成可复用的三层**：

### 4.1 平台能力层（跨行业 100% 复用）

| 能力 | 说明 |
| --- | --- |
| 组织 / 用户 / 角色 / 权限 | 三级矩阵：角色 × 菜单 × 数据范围（组织/厂区隔离 + 外部单位隔离） |
| 审批流引擎 | 可配置节点、可挂校验、可留痕；支持"限定说明"式的条件分支 |
| 消息 / 通知中心 | 待办、告警、实时推送（SignalR 类） |
| 编码引擎 | 各层单据号规则可配置 |
| 附件 / 图纸 / 版本管理 | 版本状态机（草稿→评审→确认→发布→作废）+ 变更影响分析 |
| 审计与日志 | 操作日志（不可删）+ 字段级变更日志（Before/After） |
| 看板/报表引擎 | 卡片 + 趋势 + 排名的标准组件；数据时点与陈旧标记 |
| 导入导出 | 支持批量导入（检验标准等）、CSV 导出、凭证导出 |
| 离线/幂等框架 | 离线队列 + 幂等提交 + 冲突先到先得 |
| 集成中台 | 出站队列 + 退避 + 死信 + 对账 + 配置化字段映射 |

### 4.2 行业中台层（同行业内 ~70% 复用）

| 组件 | 卷材行业 | 门/板式行业 |
| --- | --- | --- |
| 主线对象模型 | 卷（含余料、合卷、倒卷） | 部件码（含托盘码、配套包、转码） |
| 单位与计量 | 米 / 重量 / 片 | 樘 / 件 / 平方米 |
| 核心算法 | 拼板套料、自动排单 | 两段拆单、齐套分析、缺料分析 |
| 关键闸门 | 等级匹配、防多产、自动倒扣 | 齐套校验、首件拦截、认证校验 |
| 工艺路线 | 辊涂 → 裁片 | 裁板 → 热压 → 喷涂 → 装配 |

### 4.3 项目定制层（不可避免，但要控制比例）

只应该是：**特殊的闸门规则 + 特殊的报表口径 + 特殊的设备协议 + 特殊的集成接口**。
**如果定制层超过了 30%，说明前面的抽象没做够，或者这个行业不该用这套基线。**

## 5. 改造升级的切入策略（怎么找到"第一刀"）

给存量企业做改造，**最大的错误是从"我们要建一个大平台"开始**。
两个案例都给了正确的示范。

### 5.1 找"客户已投入但没被利用的资产"

案例 B 找到了激光打标机：

> **"裁板机的激光打标已经有了，但那个码现在只活在打标机里，打完就完了。
> 这套系统的第一个动作，就是把这个码激活成全厂的数据主线。"**

**通用搜索清单**：

- 已有的条码/二维码打印设备 → 能否升级成主线标识？
- 已有的地磅/称重/计米/计数设备 → 能否升级成自动报工？
- 已有的 ERP / 进销存 → 能否把它当"数据源"和"回写目标"？
- 已有的图纸/工艺文件 → 能否结构化成规则库？
- 已有的微信群/纸质流程 → 能否先搬成"可留痕的电子流程"？

> **改造升级的最佳叙事：不是我让你买新东西，是我让你已有的东西开始产生价值。**

### 5.2 找"可解耦的两段"，让串行变并行

案例 B 的**两段拆单**是全书最漂亮的一招：

```
传统：订单确认 → [等设计定稿 2~3 周，车间无活可干] → 拆单下料 → 结构生产 → 装饰 → 交期 45 天
本方案：订单确认 → [结构预拆，第 2 天即投产] ‖ [设计任务并行]
                   → 设计定稿只触发「装饰补拆」 → 装饰/齐套 → 交期 25 天
```

**通用做法**：
1. 把流程画成一条时间轴，标出**每一段在等谁**；
2. 找出"下游不依赖"的部分 → 提前启动（长周期材料预拆、备料生产）；
3. 把设计/审批/确认这类"等待"从关键路径上摘出去。

> **数字化改造中回报最高的一类项目，往往不是"提高效率"，而是"消除等待"。**
> 因为等待不产生任何价值，压缩它 100% 见效，且不需要任何设备投入。

### 5.3 找"最痛的那一个断点"

不要一开始做全厂，**只做那条"断了最痛"的链路**。

| 症状 | 断点在哪 | 第一刀 |
| --- | --- | --- |
| 客户天天问进度 | 车间不知道、销售不知道 | **报工 + 订单进度看板** |
| 月底结账对不上账 | 库存账实不符 | **出入库流水 + 盘点闭环** |
| 出了问题查不到人 | 无标识、无记录 | **主线码 + 事件档案 + 正查/反查** |
| 交期经常延误 | 排产靠经验 | **排产板 + 齐套/缺料分析** |
| 报价靠拍脑袋 | 没有成本数据 | **标准成本 + 实际成本归集** |
| 工人抵触新系统 | 报工太麻烦 | **报工粒度改造 + 计件即时可见** |
| 设计拖交期 | 串行流程 | **两段拆单（可解耦并行）** |

### 5.4 找"能让一线立刻受益"的点

案例 B 的优势三给出了这一点的标准答案：

> **"车间数字化最难的不是技术，是工人凭什么配合。
> 这套系统的答案很简单：扫一枪，计件明细当天进他的账。"**

**所以无论做哪个行业，第一个上线的东西里必须包含一个"让一线工人立刻得好处"的功能**：
计件工资实时可见 / 报工更省事 / 不用再手写台账 / 不用再挨骂。

> **顺序很重要：先让工人受益，再让工人受约束。**

## 6. 一份"新企业蓝图"的标准目录

把上面的内容组装成给新企业的方案，标准目录如下（可直接作为 `templates/` 的填写指引）：

```
第一部分  账先摆上来
  1.1 你现在最贵的三样东西是什么（用他们自己的话）
  1.2 这套东西能给你带来什么（每项都换算成钱/风险/赢单率）
  1.3 量化承诺与口径声明（什么是我们承诺的，什么是要动态推进的）

第二部分  系统怎么搭
  2.1 总体架构（接入层 / 应用层 / 能力中台层 / 边缘节点层 / 设备层）
  2.2 主线设计（主线对象是谁，正查怎么查，反查怎么查）
  2.3 断网/异常怎么办（边缘节点或离线队列）
  2.4 数据权限（组织隔离 / 集团穿透 / 外部单位三道锁）

第三部分  你的人每天怎么用
  3.1 每个角色登录第一眼看到什么
  3.2 N 个角色各自的活（按业务流程顺序排列）
  3.3 角色 × 菜单权限矩阵（让各部门负责人逐一核对签字）

第四部分  一张单走一遍
  4.1 接单与设计（含可解耦并行的部分）
  4.2 拆单与图纸（版本受控 + ECN 影响分析）
  4.3 计划与采购（齐套 + 缺料分析）
  4.4 车间（扫码/报工/防错/返工）
  4.5 质量（几级检验 + 闸门 + 让步留痕）
  4.6 仓储与发货（绑定 + 齐套闸门）
  4.7 安装与售后
  4.8 老板和财务看到什么

第五部分  多久、要什么条件
  5.1 开发完成时你验收什么（真机演示清单）
  5.2 周期怎么排（周计划 + 硬检查点）
  5.3 交付范围三层（核心主线 / 高价值 / 裁剪）+ 后移清单及理由
  5.4 双方各做什么（对价清单，每项定责任人）

第六部分  要定的事
  6.1 需要现场拍板的（含"一把手任项目主席"）
  6.2 需要会后核实的（带截止日期）
```

## 7. 十条"反模式"（两个案例都在避免的事）

| # | 反模式 | 两个案例的做法 |
| --- | --- | --- |
| 1 | 把决策权交给算法 | 排产只出草稿，**不自动派工**；"机器算、人来定" |
| 2 | 让智能模块阻塞生产 | 拼板算法超时**降级为贪心**，永远返回可用方案 |
| 3 | 硬拦设备数据 | 机联与报工差异走**软警告二次确认**（设备本身会漂移） |
| 4 | 报工粒度一刀切 | 裁板单件扫、喷涂**整托一枪**，按工序物理形态配 |
| 5 | 把系统做成"记录仪" | 强调**闸门**（防错/防呆），不只记录 |
| 6 | 让一线成为数字化的受害者 | **离线不甩锅给工人**；工人先受益（计件当天可见） |
| 7 | 一刀切隐藏菜单 | 三态可见性 + **限定说明**；一人多岗菜单取并集 |
| 8 | 边界不清，双方重复录单 | 边界表逐行签字；业务财务 vs 总账税务明确分开 |
| 9 | 静默延期 | **偏差超阈值启动范围降级，顺延的明说** |
| 10 | 用文档验收 | **不认文档，认真机**；验收测"拦不拦得住" |
