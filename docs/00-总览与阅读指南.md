# 制造企业「数字化 + Agent」交付知识库

> 本知识库来自两份真实交付物的深度拆解：一份制造执行系统的**操作手册**（132 页，五端十九模块），
> 一份**智能制造一体化方案**（含总体架构、一码贯通、权限矩阵、两段拆单、八周计划五张架构图）。
>
> 按你的要求，两份原始材料中的**企业信息、品牌、人名、客户名、供应商名、系统商名已全部剔除**，
> 只保留可迁移的**结构、机制、规则、数字与交付方法**。下文分别称 **案例 A**（卷材辊涂 / 裁片工厂）
> 与 **案例 B**（非标门定制工厂）。

## 三、如果只有 20 分钟，读这四段

**① 两份文件是同一件事的两半。**
案例 A 是**「建成之后」**——一套跑起来的系统的操作手册，回答"每个岗位每天在点什么地方"；
案例 B 是**「建成之前」**——一份把系统卖进工厂的方案，回答"这套东西凭什么值这个钱、多久能上线"。
前者给你**产品结构**，后者给你**销售逻辑 + 架构 + 交付节奏**。缺任何一半，方案都会瘸。

**② 两个案例的核心都不是"软件功能"，而是"一条主线 + 一道闸门"。**
案例 A 的主线是**卷号**（一卷服务多单、一单消耗多卷），闸门是**等级匹配 + 产能 100% 硬拦截 + 防多产倒扣**；
案例 B 的主线是**部件码**（一樘门一生不变的身份），闸门是**齐套校验 + 首件未确认不许批量报工**。
软件页面可以换、行业可以换，**"主线是什么、闸门在哪"这两个答案决定项目成败**。

**③ 智能化不是把决策交给机器，而是把「机器算」和「人拍板」分层。**
两个案例都严格遵守这条：排产算法只生成 2~3 个候选方案草稿，**不自动派工**；
算法超时自动降级为贪心策略，**宁可给一个次优解也不阻塞生产**；
Agent 的定位应当是**放大这一步的产能**（多跑候选、多做检查、多做追办），
而**不是**替代第三章那道闸门。

**④ 交付的风险不在技术，在三件"政治"事。**
一把手参与度、关键用户头两周的工时投入、设计冻结后的变更纪律。
案例 B 把这三件事写成了**对价清单**——两个月排期的每一周，都对应甲方一个必须交付的动作。
这是把"激进工期"变成"可承诺工期"的唯一办法，也是给新企业做项目时最该抄的一段。

## 四、使用建议

- **做售前/方案**：读 `02` 的价值叙事结构 + `06` 的风险与验收，直接套 `templates/06`。
- **做产品/架构**：读 `01` 的模块清单与状态机 + `03` 的七个设计题，直接套 `spec/`。
- **做实施/项目经理**：读 `05` 全篇，按 `templates/01~05` 顺序填空。
- **做 Agent 工程**：读 `04`，配合 `spec/agents.yaml` 与 `spec/gates.yaml`。
