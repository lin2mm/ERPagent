# Agent 工作流设计：能力地图与工程规范

> 这份文档回答第三个问题：**给一家新企业，怎么做出"类似的 Agent 工作流 / 智能化 / 改造升级"。**
>
> 前提认知：两个案例都已扎实做到 L3（算法优化），但**都还没到 L4（智能体协同）**。
> 这不是缺陷，而是**最好的起点**——因为 L4 不是推倒重来，
> 而是**在已有的 L2 闸门与 L3 算法之上，加一层"主动的调用者"**。

---

## 1. 核心设计哲学：三层分离

**这是全篇最重要的一条。写错这一条，Agent 项目必败。**

```
┌──────────────────────────────────────────────────────────┐
│  第三层：人（拍板层）                                       │
│  在"我的待办"里看到候选方案、证据链与影响分析，做出选择        │
│  —— 必须保留，因为责任无法交给机器                          │
├──────────────────────────────────────────────────────────┤
│  第二层：规则/闸门（裁决层）—— 永远由确定性代码实现            │
│  等级匹配 / 齐套校验 / 产能上限 / 首件拦截 / 认证校验 / 倒扣   │
│  —— Agent 不得绕过、不得修改、不得"建议"放松                 │
├──────────────────────────────────────────────────────────┤
│  第一层：Agent（提议层）                                    │
│  感知 → 检索 → 推理 → 生成候选 → 附证据 → 提交待办           │
│  —— 只做"提议"，不做"裁决"                                  │
└──────────────────────────────────────────────────────────┘
```

**一句话记忆**：

> ## **Agent 提议，规则裁决，人拍板。**

### 1.1 为什么必须是这三层（用两个案例的证据）

| 证据（来自案例） | 推导出的规则 |
| --- | --- |
| 案例 A 的自动排单**只生成草稿、不做自动派工**："产线、日期与顺序仍由生产部长决定，机器不替代人工决策" | **排产类 Agent 只能输出候选方案**，采纳动作留给有权限的人 |
| 案例 A 拼板算法"超时或失败自动降级为贪心策略，保证总能给出可用方案，不阻塞生产" | **Agent 必须有降级路径**，宁可给次优解也不能卡住产线 |
| 案例 A 机联报工超容差走**软警告二次确认**而非硬拦截 | **人机数据冲突走确认而非阻断**（设备也会漂移） |
| 案例 B "首件没确认，这条工序的批量报工被系统死死拦住" | **闸门是系统的责任，不能让 Agent 来"判断该不该拦"** |
| 案例 B 断网冲突进**裁决队列，每条带两侧证据，班组长在线裁决** | Agent 产出冲突时，同样应**带证据进待办**，而不是自行裁定 |
| 案例 A 操作日志"不可删除"，审计记录操作人/IP/动作/目标 | **Agent 必须作为"虚拟账号"留痕**，且行为可复盘 |
| 案例 B "系统不碰发工资，但明细、勾稽、稽核全备" | **Agent 不碰利益分配决策**，只提供依据 |

## 2. Agent 架构：五层 + 一个总闸

```
┌─────────────────────────────────────────────────────────────────┐
│ ⑤ 执行层  Execution                                              │
│   通过既有业务 API 执行（幂等键 / 干跑模式 / 虚拟账号审计）        │
│   ★ 禁止：直连数据库写入、跳过服务层校验、修改历史已报工数据        │
├─────────────────────────────────────────────────────────────────┤
│ ④ 治理层  Guardrails  ← 横切所有层                               │
│   权限继承 · 闸门不可绕 · 金额/数量阈值 · 需人审批清单             │
│   · 提示注入防护 · 工具白名单 · 降级与熔断                        │
├─────────────────────────────────────────────────────────────────┤
│ ③ 规划层  Planning                                               │
│   任务分解 → 工具选择 → 多方案生成 → 影响分析 → 证据装配          │
│   ★ 输出必须是「候选方案 + 依据 + 影响范围」，不是「结论」          │
├─────────────────────────────────────────────────────────────────┤
│ ② 认知层  Knowledge                                              │
│   规则库（工艺/约束/口径）· 案例库（历史处置）· 文档库（SOP/图纸）  │
│   ★ 口径必须与看板/报表同源，避免"两个数"                         │
├─────────────────────────────────────────────────────────────────┤
│ ① 感知层  Perception                                             │
│   事件订阅：订单接入 / 报工 / 检验 / 异常上报 / 预警 / 超期        │
│   定时扫描：账龄 / 呆滞 / 齐套缺口 / 保养到期 / 合同月份           │
└─────────────────────────────────────────────────────────────────┘
                              ↓ 所有写动作
                     ══ 系统硬闸门（不可绕） ══
```

**关键：Agent 位于闸门的"上方"，而不是"旁边"。**
它可以帮助人在**到达闸门之前**就把事情做对（提前发现、提前纠偏），
但**永远不能替人穿过闸门**。

## 3. Agent 清单（14 个，按业务族）

每个 Agent 的规格：`触发 → 输入 → 工具 → 输出 → 护栏 → 度量`。

### 族 A · 计划与排产

#### A1 排产参谋

| 项 | 内容 |
| --- | --- |
| **触发** | 新订单进入"待规划"；或生产部长在计划编排中心点击"参谋一下" |
| **输入** | 待规划订单行、可用卷料/物料（含在途）、呆滞分档、产能日历、交期 |
| **工具** | 自动排单引擎（可调权重）、拼板/套料算法、卷料侧栏查询 |
| **输出** | **2~3 个候选计划方案**，每个附：交期达成率、呆滞消化率、预计成材率、换卷换刀次数、**风险提示**；并用自然语言解释"为什么推荐方案 B" |
| **护栏** | 只生成草稿，**不自动派工**；权重变化必须显式记录；产能校验走系统硬闸门 |
| **度量** | 方案采纳率 · 采纳后交期准时率 · 呆滞消化量 · 排产耗时下降 |

> 对应案例 A 的"权重配置 + 候选方案 + 采纳/拒绝"。**这是最容易落地、也最容易证明价值的 Agent。**

#### A2 齐套 / 缺料追办

| 项 | 内容 |
| --- | --- |
| **触发** | 每日定时；或订单交期前 N 天；或缺口新增 |
| **输入** | 订单 BOM 齐套视图、库存、在途、采购交期、外协进度 |
| **工具** | 齐套查询、缺料分析（需求−库存−在途=缺口）、采购申请创建、消息推送 |
| **输出** | **催办清单**（缺什么、缺多少、卡在哪道工序或哪张采购单、该找谁、建议动作与截止日）；一键转采购申请草稿 |
| **护栏** | 只创建**草稿**与**待办**；不代替采购员下单；不修改交期（只提示风险） |
| **度量** | 齐套缺口提前暴露天数 · 因缺件导致的停工次数 · 交期延误率 |

> 对应案例 B 的"缺口一键转采购申请"与"花件交期单独预警"（关键路径件单独成列）。

#### A3 呆滞消化

| 项 | 内容 |
| --- | --- |
| **触发** | 每周；或卷料跨入下一呆滞档（30/90/180） |
| **输入** | 呆滞清单（卷号、库龄、重量、金额、等级、规格）、在制与在手订单 |
| **工具** | 呆滞查询、拼板/改裁算法、降级规则、客户可发等级 |
| **输出** | **消化建议**：优先改裁成哪些订单的规格、可否合卷、可否降级发某类客户、预计资金释放 |
| **护栏** | 等级降级走系统合规流程（单向 + 留痕）；**不得建议"降级卖给不匹配的客户"** |
| **度量** | 90/180 天呆滞金额下降 · 资金占用周转天数 |

### 族 B · 现场与异常

#### B1 异常聚合与处置参谋

| 项 | 内容 |
| --- | --- |
| **触发** | 工位/设备上报异常；或告警级别升级 |
| **输入** | 异常类型与描述、涉事卷/工单/工位、历史同类处置记录、当前产能与在制 |
| **工具** | 异常聚合查询、历史处置检索、指派接口、知识库 |
| **输出** | **分类与定级建议 + 推荐处置路径 + 历史相似案例**；指派建议；一键建单 |
| **护栏** | 定级与指派可由人覆盖；**质量类异常不得直接置为"已解决"** |
| **度量** | 平均响应时长 · 平均处置时长 · 重复异常下降率 |

> **这个 Agent 的价值在于"翻译"**：把工人用口语写的"上料跑偏了"映射到规范的异常类型与处置路径。

#### B2 插单 / 改单影响评估

| 项 | 内容 |
| --- | --- |
| **触发** | 提交插单申请；或提交改单（换卷/调量/拆单/撤销） |
| **输入** | 申请内容、当前在制、产线占用、物料可用性、受影响订单与其交期 |
| **工具** | 在制查询、产能模拟、交期重算、物料可用性校验 |
| **输出** | **影响评估报告**：影响哪些订单、各延期多少天、需要追加什么、建议插队级别（P0/P1/P2）与理由 |
| **护栏** | 仅生成评估；审批与优先级调整由人执行；**插单决策链永久保留**（考核依据） |
| **度量** | 插单审批耗时 · 评估准确度（实际影响 vs 预测）· 插单频次 |

> 案例 A 的"系统自动评估在制卷剩余长度是否满足、是否需要追加调拨"就是这一步的雏形。

#### B3 设备预警与维保参谋

| 项 | 内容 |
| --- | --- |
| **触发** | 机联心跳异常；或保养计划到期；或维修工单重复出现 |
| **输入** | 设备心跳/计数/停机记录、维修工单历史、备件库存、保养计划 |
| **工具** | 机联状态查询、维修历史、备件查询、保养计划 |
| **输出** | 预警与建议（提前保养/备件备货/更换周期调整），附依据 |
| **护栏** | 不自动停线；不自动采购备件 |
| **度量** | 非计划停机时长 · 备件缺货次数 · 维修重复率 |

### 族 C · 质量与追溯

#### C1 缺陷规避与改裁参谋 ★

| 项 | 内容 |
| --- | --- |
| **触发** | 卷料进入待裁；或质检员登记缺陷；或生产部长打开拼板方案 |
| **输入** | 缺陷记录（类型/严重度/**位置区间**）、订单规格需求、可用卷宽 |
| **工具** | 缺陷查询、拼板/套料算法（带缺陷区间规避硬约束） |
| **输出** | **规避或改裁方案**（例："跑偏 2 公分区域改裁 42×578 规格"），含成材率、接缝数、余料 |
| **护栏** | 方案须满足硬约束（接缝数 ≤2、成材率 >92%）；**采纳走人** |
| **度量** | 成材率提升 · 因缺陷导致的报废重量下降 · 改裁决策耗时 |

> 这个 Agent 的前提是**缺陷已经被做成"带位置的区间"**（案例 A 的做法）。
> **如果企业的缺陷还只是"合格/不合格"的布尔值，先做数据改造，不要硬上 Agent。**

#### C2 质量事故溯源

| 项 | 内容 |
| --- | --- |
| **触发** | 输入批次号 / 供应商 / 设备 / 时间区间，发起溯源 |
| **输入** | 主线标识谱系、批次、工艺参数、检验记录、发货记录、责任人 |
| **工具** | 正查（扫任意码出全生命周期档案）、反查（批次→受影响范围）、台账导出 |
| **输出** | **受影响范围清单**（哪些樘/片/卷、哪些订单、哪些项目/客户）+ 冻结建议 + 可导出台账 |
| **护栏** | 冻结为**建议**，执行需人确认；导出台账**记录审计** |
| **度量** | 溯源耗时（目标：分钟级）· 召回范围准确度 · 项目验收一次通过率 |

> 对应案例 B 的核心卖点："把批次号输进去，几分钟锁定受影响的樘和项目，一键冻结，台账直接导出。"
> **这是唯一一个"能直接换来订单"的 Agent，做政府/医院/学校项目的企业尤其值得优先上。**

#### C3 让步放行 / 特采预审

| 项 | 内容 |
| --- | --- |
| **触发** | 提交不合格品处理单或放行申请 |
| **输入** | 不合格情况、检验数据、客户等级与可发范围、历史同类让步记录、客户特殊约定 |
| **工具** | 检验台账、客户等级规则、历史特采检索 |
| **输出** | **预审意见**：证据汇总、规则比对结果、风险提示、建议（报废/特采/让步）+ 相似先例 |
| **护栏** | **绝不自动批准**；审批链完整保留；特采必留档 |
| **度量** | 审批耗时 · 特采比例变化 · 因特采导致的客诉率 |

### 族 D · 商务与资金

#### D1 配置报价参谋

| 项 | 内容 |
| --- | --- |
| **触发** | 销售发起选型；或客户询价进入线索池 |
| **输入** | 选型配置、量尺数据、约束规则、历史成交价、当前材料成本 |
| **工具** | 配置器引擎（约束校验）、标准成本、历史报价检索 |
| **输出** | **报价草稿**（含配置校验结果、成本参考、毛利提示、交期区间）+ 偏离历史价的说明 |
| **护栏** | 折扣/低价必须走审批；**不承诺交期**（只给区间，由 A/B 族确认） |
| **度量** | 报价耗时 · 报价一次通过率 · 毛利率偏差 |

#### D2 收款催办

| 项 | 内容 |
| --- | --- |
| **触发** | 账龄跨档（30/60/90/180 天）；或合同约定收款节点到期 |
| **输入** | 应收台账、账龄、客户信用额度、历史回款行为、合同节点 |
| **工具** | 应收查询、客户 360、消息/待办推送 |
| **输出** | **催办任务**（给销售或财务）：金额、超期天数、建议动作、沟通要点草稿 |
| **护栏** | **不直接联系客户**（对外沟通必须由人发出）；不动信用额度 |
| **度量** | 平均回款周期 · 超期金额占比 · 催办响应率 |

#### D3 交期承诺参谋

| 项 | 内容 |
| --- | --- |
| **触发** | 销售需要给客户回交期 |
| **输入** | 当前产能负载、在制、物料可用与在途、排产候选结果、历史同类订单实际周期 |
| **工具** | 排产模拟、产能日历、物料查询 |
| **输出** | **可承诺交期区间**（乐观/保守）+ 依据 + 风险点（哪个环节可能卡） |
| **护栏** | 只给区间与依据；**不对外发送**；不替代排产决策 |
| **度量** | 交期承诺达成率 · 因交期失约的客诉率 |

> 这个 Agent 直接支撑案例 B 优势五："客户问进度，销售一秒回答。"

### 族 E · 知识与管理

#### E1 工艺 / SOP / 图纸问答

| 项 | 内容 |
| --- | --- |
| **触发** | 工位端点击"问一下"；或关键字检索 |
| **输入** | 当前工单工序、设备型号、产品规格 |
| **工具** | SOP 文档库、图纸库（**按版本过滤**）、工艺规则库 |
| **输出** | 答案 + **引用来源（文档编号 + 版本 + 页码/图号）** |
| **护栏** | **必须带引用**；图纸只能返回**当前有效版本**；涉及安全参数的答案需二次确认提示 |
| **度量** | 问答命中率 · 因用错版本导致的返工次数 · 一线使用频次 |

> 对应案例 B："现场扫部件码看到的一定是正确版本，图纸版本误用事故的目标是零。"
> **带引用的 RAG 在这里是刚需，不是锦上添花——车间不能拿到一个"大概是"的答案。**

#### E2 经营日报 / 例会参谋

| 项 | 内容 |
| --- | --- |
| **触发** | 每日定时；或例会看板打开 |
| **输入** | 与看板**同源**的指标数据、异常清单、待办、趋势 |
| **工具** | 报表查询、指标口径库、异常/待办查询 |
| **输出** | 结构化简报：**发生了什么 → 可能的原因 → 建议关注什么 → 建议谁去处理**（每条带数据来源与时点） |
| **护栏** | **口径必须与驾驶舱同源**；结论措辞不得超出数据支撑；**数据时点必须展示** |
| **度量** | 例会准备耗时 · 待办转化率 · 用户主动阅读率 |

> 案例 A 的会议看板已经很接近：四类例会看板、30 秒刷新、右上角显示"数据更新时间"与陈旧标记。
> Agent 在此之上的增量是：**把数字翻译成"所以呢"**。

## 4. 工程规范：九条硬规矩

| # | 规矩 | 原因 / 案例依据 |
| --- | --- | --- |
| **1** | **写操作一律走既有业务 API，禁止直连数据库** | 否则绕过服务层校验，等于自己拆掉了闸门。案例 A 的每条业务规则都写在服务层。 |
| **2** | **Agent 以"虚拟账号"接入，权限等同其服务的岗位，写操作全程审计** | 案例 A："操作日志不可删除"，记录操作人/IP/动作/目标。Agent 也必须能被审计。 |
| **3** | **幂等** | 案例 A 报工幂等设计（离线补传不会重复报工）、ERP 同步失败重推不重复。Agent 重试同理。 |
| **4** | **必须有降级路径，且永不阻塞生产** | 案例 A 拼板算法超时**降级贪心**："保证总能给出可用方案，不阻塞生产。" Agent 失败 → 回到人工可用状态。 |
| **5** | **候选方案 + 证据，而不是结论** | 案例 A 排单"生成 2~3 个候选"。**没有候选，就没有可选择的责任边界。** |
| **6** | **输出带数据时点与来源** | 案例 A 会议看板标注"数据更新时间"与陈旧状态，避免例会口径争议。 |
| **7** | **干跑（dry-run）模式** | 任何写动作先在干跑模式产出 diff 给人看，确认后再执行。 |
| **8** | **阈值护栏：金额/数量/等级变更超阈值必须人工审批** | 参考案例 B 的 ECN 变更流程与"影响分析自动列在制订单"。 |
| **9** | **提示注入防护 + 工具白名单** | 来自工单备注、客户留言、图纸文本的内容一律视为**不可信输入**，不得据此越权调用工具。 |

### 4.1 一个必须明确的"禁止清单"

```
✗ 绕过或建议绕过任何硬闸门（等级匹配、齐套、产能上限、首件拦截、认证校验）
✗ 修改已报工 / 已审核 / 已执行的冻结数据（案例 A：已报工数据冻结不可改）
✗ 直接对外发送消息（客户、供应商、经销商）——对外口径一律由人发出
✗ 决定与个人利益相关的分配（工资、计件单价、罚款）—— 案例 B："系统不碰发工资"
✗ 自动批准任何质量放行（特采、让步接收）
✗ 在数据缺失时"补齐"或推测事实值（宁可说"缺数据"，不能编数字）
✗ 用自然语言生成规则判定结果（判定必须来自确定性代码，Agent 只做解释）
```

### 4.2 Agent 输出的标准结构（建议统一）

```yaml
agent: scheduling_copilot
trigger: order_ready_for_planning
data_as_of: 2026-09-11T09:30:00+08:00     # 数据时点（规矩 6）
summary: 为 3 张订单生成 3 个候选计划方案
candidates:                                # 候选方案（规矩 5）
  - id: A
    score: 86
    metrics: { on_time_rate: 0.94, sluggish_consumption_kg: 1820, yield_rate: 0.938 }
    risks: ["8/28 前需完成辊涂，否则影响交期"]
  - id: B ...
evidence:                                  # 证据链
  - type: coil_inventory
    ref: 卷料侧栏查询(2026-09-11 09:30)
  - type: rule
    ref: 产能上限规则 v3 / 呆滞优先权重 0.30
confidence: medium
limits: "仅生成草稿，派工需生产部长确认"
```

## 5. 落地路径：四波推进（不要一次做 14 个）

### 第一波（0–6 周）：**只读参谋**，零写权限

| Agent | 为什么先做 |
| --- | --- |
| **E2 经营日报/例会参谋** | 只读、见效快、面向管理层（**老板最快感受到价值**） |
| **E1 工艺/SOP 问答（带引用）** | 只读、一线立刻可用、**天然不需要写权限** |
| **A2 齐套/缺料追办（只出清单，不建单）** | 直击交期痛点、无写风险 |

**目标**：让企业先相信"它说得对"，同时把知识库/口径库/工具层建起来。
**关键交付**：Agent 输出必须**带数据时点与来源**（规矩 6），否则第一次报错就失去信任。

### 第二波（6–14 周）：**候选方案类**，写"草稿"不写"生效"

| Agent | 写什么 |
| --- | --- |
| **A1 排产参谋** | 生成计划草稿 |
| **B1 异常聚合与处置参谋** | 生成处置建议 + 建单草稿 |
| **B2 插单/改单影响评估** | 生成评估报告 |
| **C1 缺陷规避与改裁参谋** | 生成方案草稿 |
| **C3 让步放行预审** | 生成预审意见 |

**目标**：把"机器算、人来定"从排产一个点，扩展到多个决策点。
**关键交付**：每个 Agent 都要能回答"**采纳率是多少、采纳后结果比人工好还是差**"。

### 第三波（14–26 周）：**闭环执行 + 主动追办**

| Agent | 闭环形态 |
| --- | --- |
| **A3 呆滞消化** | 建议 → 采纳 → 生成改裁/合卷草稿 |
| **B3 设备预警与维保** | 预警 → 建保养计划/维修工单草稿 |
| **D2 收款催办** | 生成待办并跟踪到关闭 |
| **D1 配置报价参谋** | 报价草稿 → 审批流 |
| **D3 交期承诺参谋** | 交期区间 → 写入订单交期建议 |

**目标**：从"等人来问"变成"主动推送待办"。
**关键交付**：**待办转化率**成为核心指标——如果推了没人处理，说明推送的时机或对象错了。

### 第四波（26 周+）：**跨系统协同与自省**

- **C2 质量事故溯源**（需要完整的谱系数据，所以放最后）；
- **跨 Agent 协同**：如"交期风险"由 A2（缺料）+ A1（排产）+ D3（交期）联动给出统一结论；
- **Agent 效果复盘**：定期比对人机决策差异，把"人经常否决 Agent 的某类建议"变成规则或权重调整。

> **节奏原则：先只读、再草稿、再闭环、最后跨系统。**
> 每一波都在为下一波铺路——**没有第一波建立的知识库和信任，第二波会被当成玩具。**

## 6. 评测：怎么证明 Agent 有用

### 6.1 四类指标

| 类别 | 指标 | 说明 |
| --- | --- | --- |
| **质量** | 幻觉率（事实错误占比）· 引用准确率 · 方案可行性（被判"不可行"的比例） | **引用准确率是关键**：错了要能查出来 |
| **采纳** | 建议采纳率 · 候选方案采纳分布（是否总选第一个？） | 总是选第一个可能说明候选没差异，或人没在看 |
| **效果** | 交期准时率 · 成材率 · 呆滞金额 · 平均处置时长 · 回款周期 | **必须与"上 Agent 前"做同期对比** |
| **信任** | 主动使用频次 · 用户否决理由分布 · 覆盖岗位数 | 否决理由是**最有价值的训练数据** |

### 6.2 评测方法（照抄案例的验收思路）

案例 B 的验收方式是"**不认文档，认真机**"，且包含**负面测试**。Agent 评测同理：

```
正面测试：给一个真实场景，看它能否给出可采纳的方案
负面测试：给一个必然违规的请求，看它会不会越界
  例：让排产 Agent 把已超产能的产线再排一单 → 必须拒绝或提示硬闸门
  例：让问答 Agent 引用一张已作废的图纸 → 必须返回当前有效版本
  例：让溯源 Agent 报出"缺少批次记录"的结论 → 必须说"缺数据"而非推测
回归测试：同一批历史场景，每次模型/提示/规则变更后重跑，比对结论差异
对照测试：同一场景，人独立决策 vs Agent 建议，比对结果（这是"效果"类指标的唯一来源）
```

### 6.3 上线前的验收清单（逐条打勾）

- [ ] 每个 Agent 都有明确的**只读/草稿/闭环**权限声明
- [ ] 所有写动作走既有 API，**无任何直连数据库写入**
- [ ] Agent 使用**虚拟账号**，操作日志可查、不可删
- [ ] 幂等键已实现，重试不会产生重复单据
- [ ] 有降级路径：Agent 不可用时，原有人工流程完全可用
- [ ] 输出统一带 `data_as_of`（数据时点）与 `evidence`（依据）
- [ ] 决策类输出为**候选方案**（≥2 个），并附风险提示
- [ ] 干跑模式已验证，diff 可读
- [ ] 阈值护栏与"需人审批清单"已与客户确认
- [ ] 负面测试用例全部通过（不越权、不编数据、不绕闸门）
- [ ] 提示注入防护与工具白名单已启用
- [ ] 口径与驾驶舱/报表**同源**，无"两个数"

## 7. 这两个案例为什么是上 Agent 的理想起点

把第 1 节的哲学落到这两个案例上，会发现它们已经**无意中为 Agent 铺好了全部地基**：

| 已有地基 | 来自 | 对 Agent 的意义 |
| --- | --- | --- |
| **状态机与枚举字典** | 案例 A 的 17 态 + 附录状态字典 | 界定了 Agent 的**行动空间**：它在哪些状态能做什么，一目了然 |
| **硬闸门在代码里** | 等级匹配、齐套、产能、首件 | Agent **不需要判断合规性**，只需提议；闸门自动兜底 |
| **"候选方案 + 采纳"的交互范式** | 案例 A 自动排单/拼板 | 用户**已经习惯**"机器给方案、我来定"，Agent 的交互不用教育 |
| **完整的权限与审计** | 9/13 角色矩阵 + 不可删日志 | Agent 可以安全地以虚拟账号接入 |
| **待办驱动的工作台** | 两个案例都有 | Agent 的输出有**天然的落点**（进待办），不需要发明新界面 |
| **数据时点与陈旧标记** | 案例 A 会议看板 | 用户已被训练成"看时点"，对 Agent 输出同样适用 |
| **离线/幂等/冲突裁决** | 两个案例都有 | Agent 的任务队列可以复用同一套可靠性机制 |
| **知识资产已结构化** | 案例 B 的规则库/图纸库/公式版本化 | RAG 有高质量的语料，且**带版本**（引用可到版本级） |

**所以对新企业的最优路径不是"先做 Agent"，而是：**

```
第一步：把 L2 的闸门和自动联动做扎实（1–2 个季度）
        —— 让系统成为"确定的、可预期的执行环境"
第二步：把 L3 的算法做出来，并采用"候选方案 + 人采纳"的交互
        —— 让用户习惯"机器算、人来定"
第三步：在此基础上叠加 Agent
        —— 它只是"更主动、更会解释、更能跨模块调用"的那一层
```

> **跳步的代价**：在一家还在用 Excel 的企业直接上 Agent，
> 你会得到一个"很聪明但没有任何抓手"的助手——它能说，但没人敢让它做，因为它下面没有闸门。

## 8. 交付一份"Agent 方案"的标准目录

给新企业做 Agent 化方案时，按这个目录写：

```
一、你现在处于哪一级（L0–L4 自评）
    1.1 现状盘点：数据在哪、谁在录、录得准不准
    1.2 结论：本次要上到哪一级，不做什么

二、你已有的地基（关键——先讲复用，再讲新增）
    2.1 已有的标识体系 / 设备 / 系统 / 文档
    2.2 已被结构化到什么程度
    2.3 缺什么地基，必须先补（诚实列出）

三、第一批 Agent 清单（3 个以内）
    3.1 每个 Agent 的：触发 / 输入 / 工具 / 输出 / 护栏 / 度量
    3.2 权限声明：只读 / 草稿 / 闭环
    3.3 与现有流程的关系（替换了谁的一步？还是新增了一步？）

四、三层分离与闸门清单
    4.1 Agent 提议什么
    4.2 规则裁决什么（列出全部硬闸门）
    4.3 人拍板什么（列出必须人工确认的动作）

五、工程规范与验收
    5.1 九条硬规矩逐条对照
    5.2 禁止清单
    5.3 负面测试用例
    5.4 上线前验收清单

六、评测与迭代
    6.1 四类指标与基线值
    6.2 对照测试方案
    6.3 否决理由如何反哺规则与权重

七、节奏与对价
    7.1 四波推进的时间表
    7.2 每一波"什么算成了"
    7.3 需要企业方配合的事项（每项定责任人）
```
