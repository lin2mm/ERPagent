# 原方案评分报告

> 评分对象：两份原始交付物（已脱敏）。
> **案例 A** = 卷材制造执行系统操作手册（132 页 / 5 端 / 19 章 / 4 附录）
> **案例 B** = 非标定制品智能制造一体化方案（6 部分 + 5 张架构图）
>
> 评分方式：两轮——先按**统一交付物质量量表**（100 分制，7 维）打分，再按**转用价值**单独评估。
> 两者体裁不同（操作手册 vs 售前方案），因此量表刻意选取对两者都成立的维度，
> 并在每一维的评语中说明"以它的自身定位衡量"。

## 一、评分量表（7 维 / 100 分）

| 维度 | 权重 | 判定问题 |
| --- | --- | --- |

| **D7 可复用与可迁移** | 10 | 抽掉行业外壳后，方法论还有多少价值？ |

## 二、案例 A · 卷材制造执行系统操作手册

| 维度 | 得分 | 评语 |
| --- | --- | --- |
| **D1 定位达成度** | **13.5 / 15** | 手册声称服务"九类岗位、五端、按端按角色按流程逐步讲解"，并且在开头就用**"岗位 × 建议阅读章节"表**把这件事兑现了——每个人只看自己该看的。收尾还有四份附录（FAQ / 状态字典 / 权限矩阵 / 操作规范）。**扣分点**：只讲"怎么用"，几乎没有讲"为什么这么设计"和"规则可不可配、谁能改、改了影响什么"。读者能操作，但无法判断边界。 |
| **D2 内容完整度** | **13.5 / 15** | 19 章覆盖接单→收款全链，含设备维护、能耗、采购、财务凭证导出——**覆盖面已超出"操作手册"的常规水准**。但发现一处硬伤：正文称卷料为"**17 态**生命周期"，附录 B 的状态字典却只列到 14 项（值 0–12、15、16），**13 和 14 缺失**，两处对不上。作为"唯一权威速查表"，这类不一致会在开发与测试环节被放大。 |
| **D3 结构与逻辑** | **14 / 15** | "先总后分、先流程后模块"的分层非常干净：第 1–3 章总纲（其中第 3 章是全书的"地图"），第 4–16 章按菜单顺序逐模块，第 17–19 章多端与系统。每章统一按"功能概述 → 界面认识 → 操作步骤 → 字段说明 → 注意事项"编写，**形成可预期的阅读节奏**。扣分：第 4 章（工作台）相对单薄；第 3 章的 12 环节与后续章节并非一对一映射，读者需要自己找对应章。 |
| **D4 可执行性** | **18 / 20** | **本册最强项。** 每章都有编号步骤、字段含义表、注意事项分栏；FAQ 按登录/生产/质量仓储/系统管理四类问答；开头给出终端与浏览器的最低分辨率要求。几乎可以当"新人上岗训练包"直接用。扣分：部分关键操作**没说清权限前提**（"改单由谁审批""特采谁能批"散落各处，需回附录 C 反查）；缺少性能与容量口径（多少卷、多少并发）。 |
| **D5 风险与边界** | **12.5 / 15** | 做得好的是**系统边界**：给出了与外部 ERP 的协作边界表（谁写谁、谁只读），并明确声明"本系统财务定位为业务财务，总账/发票/税务以既有系统为准"——这是很多同类交付物不敢写的一句。数据侧也有底牌：**已报工数据冻结不可改**、操作日志不可删除、字段级变更留痕。扣分：**缺少上线与运营层面的风险说明**（数据迁移失败怎么办、闸门误拦怎么办、离线队列积压怎么办），也缺少对"误用场景"的防御性提示。 |
| **D6 表达与专业度** | **9 / 10** | 术语统一、颜色语义统一并提炼成口诀（"绿正常、蓝在动、黄要防、橙要急、红必停"）、全局使用同一套列表页骨架与弹窗惯例。发现一处交叉引用错误：正文称"ERP 同步详见 19.4 节"，实际 ERP 同步是 19.5，19.4 是机联设备——**这类错引在操作手册里会直接浪费一线的时间**。 |
| **D7 可复用与可迁移** | **9 / 10** | 抽掉行业后剩下的东西很硬：状态字典 + 事件档案的写法、颜色语义体系、"候选方案 + 人工采纳"的算法交互、闸门清单（等级匹配/防多产/产能拦截/换卷校验）、ERP 边界表。**附录 B 状态字典速查表的写法尤其值得抄**——一份文档同时充当开发文档、测试用例来源和培训教材。 |
| **合计** | **89.5 / 100** | **A 级** |

**一句话总评**：这是一份**成熟度极高、但天花板受体裁限制的产品说明书**。它把"系统现在长什么样、你要怎么点"讲到了近乎无可挑剔；短板集中在"为什么"与"可配置性/边界"上——它是一本**使用手册**，不是一本**设计说明书**。

## 三、案例 B · 非标定制品智能制造一体化方案

| 维度 | 得分 | 评语 |
| --- | --- | --- |
| **D1 定位达成度** | **14.5 / 15** | 作为一份"要说服客户掏钱并同时锁定工期与责任"的方案，它把三件事一次做到了：**价值叙事**（六项优势，每项都换算成交期/资金/赢单率）、**架构可信度**（五层架构图 + 一码贯通图）、**交付可承诺**（八周计划 + 范围三层 + 双方配合清单 + 现场拍板事项）。结尾"要定的事"把决策项列成清单并要求当场拍板——**这是把售前方案写成项目章程起点的做法**。 |
| **D2 内容完整度** | **12 / 15** | 六大部分 + 5 张图覆盖业务、架构、角色、流程、交付与商务，密度很高。但有三处实打实的缺口：**① 非功能需求缺失**（性能/并发/容量/可用性一个字没提）；**② 集成接口缺清单**（只提出"打标机协议第一周确认"，没有接口明细表——对比案例 A 的 ERP 边界表，这里明显更薄）；**③ 数据迁移只到策略层**（"导不出就降级为只迁汇总余额"，没有字段级映射与核对方法）。 |
| **D3 结构与逻辑** | **14.5 / 15** | 六章递进极其顺：**先说结论（账摆上桌）→ 系统怎么搭 → 你的人每天怎么用 → 一樘门走一遍 → 多久要什么条件 → 要定的事**。这是"客户视角"而非"乙方视角"的组织顺序——**先讲他能得到什么，再讲我们怎么做，最后讲需要他做什么**。角色章节按业务流程顺序排列，菜单也按生意顺序排列，前后一致。 |
| **D4 可执行性** | **17.5 / 20** | 八周计划细化到周（含 W4/W6 两个硬检查点与两次真机演示）、双方配合清单每项都是"可验证的动词 + 责任人 + 时点"、范围分成三层并明确后移清单与理由、验收清单直接是五条可当场执行的真机动作。**"后移清单就是两个月承诺的对价"这一句，把整份方案从宣传册变成了合同附件。** 扣分：只有"五条线满编 25–30 人"，**没有 WBS 与人力投入表**；偏差阈值只说"超阈值就降级"，未给具体数值。 |
| **D5 风险与边界** | **12 / 15** | 亮点是**把风险写成前提条件**："蓝图每拖一周，开发窗口就少一周""数据不齐，试点验证就是失真的""这条不通，打码主线直接受冲击"——每一条风险都指向一个具体动作和责任人，比一张风险矩阵有用得多。也有"不预埋拍脑袋的日期""不静默延期"的诚实声明。扣分：**没有独立的风险登记册**（风险散落在配合清单里，无法按影响度排序）；**没有失败预警信号**（什么迹象出现说明项目要黄）；没有说清"甲方不配合时乙方的退出机制"。 |
| **D6 表达与专业度** | **9.5 / 10** | **两份材料里表达最强的一份。** "先把账摆在桌面上""打完就完了""工人凭什么配合""不认文档，认真机""顺延的明说，不静默延期"——全部是说人话、且能记住的句子。5 张图（总体架构 / 一码贯通 / 权限矩阵 / 两段拆单时间轴 / 八周计划）各自承担一个论点，信息层级清楚。扣分：正文偶有口语化偏重（"别到了现场才发现装不上"），在正式合同附件中需要再收敛一次。 |
| **D7 可复用与可迁移** | **9.5 / 10** | 可直接复用的部分最多：方案目录结构、六项优势的叙述法、**两段拆单（"找可解耦的两段，让串行变并行"）**、一码贯通与转码接力、边缘节点断网方案、角色 × 菜单权限矩阵、**范围三层 + 后移清单**、**双方配合清单**、"不认文档认真机"的验收法。这些几乎与行业无关。 |
| **合计** | **89 / 100** | **A 级** |

**一句话总评**：这是一份**范本级的售前 + 交付方案**。它最厉害的不是功能清单，而是**把"承诺"写成了"对价"**——每一周的工期都对应甲方一个可验证的动作，每一项不做的事都有理由且被要求当场认可。短板在工程侧：非功能需求、接口明细、数据迁移细节、风险管理文档。

## 四、同分不同质：两份材料的强弱画像

两份总分接近（89.5 / 89），但**优势维度完全互补**：

```
维度                   权重   案例A   案例B   差异
D1 定位达成度           15    13.5    14.5    B 略强
D2 内容完整度           15    13.5    12.0    A 强（B 缺非功能/接口/迁移细节）
D3 结构与逻辑           15    14.0    14.5    B 略强
D4 可执行性             20    18.0    17.5    A 略强（B 缺 WBS 与阈值）
D5 风险与边界           15    12.5    12.0    接近，短板不同
D6 表达与专业度         10     9.0     9.5    B 强（语言与图示）
D7 可复用与可迁移       10     9.0     9.5    B 略强
─────────────────────────────────────────────────
合计                   100    89.5    89.0
```

**结论：A 是"把已建成的东西说到无懈可击"，B 是"把未建成的东西说到让人敢签"。**
两者几乎不重叠——**一份做产品基线，一份做交付方法，合起来正好是一套完整的打法。**

### 共同的三个短板（两份都没做好的事）

| # | 共同短板 | 具体表现 | 对第三家企业的影响 |
| --- | --- | --- | --- |
| 1 | **非功能需求缺失** | 性能、并发、容量、可用性、备份恢复，两份都没写 | 上线后才知道撑不撑得住；扩容成本无法预估 |
| 2 | **没有独立的风险登记册** | 风险散落在注意事项/配合清单里，未按影响度排序，也没有失败预警信号 | 项目出问题时只能救火，无法提前干预 |
| 3 | **数据治理只到策略层** | 都提到"要清洗主数据"，但没有字段级标准、唯一性规则、责任矩阵、质量度量 | 数据问题会在上线后 3 个月集中爆发 |

## 五、转用价值评估（换个角度看）

如果目标是"**给一家新企业做类似的系统与 Agent 化升级**"，那么两份材料的价值不是"文档写得好不好"，而是"**能直接搬走多少**"。

| 转用资产 | 案例 A | 案例 B |
| --- | --- | --- |
| 需求基线（功能清单可直接当开发范围） | ★★★★★ | ★★★★ |
| 数据结构（状态机 / 事件 / 枚举字典） | ★★★★★ | ★★★☆ |
| 闸门与校验规则（可直接抄的硬约束） | ★★★★★ | ★★★★☆ |
| 算法设计（约束、权重、降级策略） | ★★★★★ | ★★★ |
| 价值叙事与售前话术 | ★★☆ | ★★★★★ |
| 架构分层与集成方案 | ★★★☆ | ★★★★★ |
| 权限模型 | ★★★★ | ★★★★★ |
| 交付节奏与商务对价 | ★★ | ★★★★★ |
| 验收方法 | ★★★★ | ★★★★★ |
| 风险与治理文档 | ★★☆ | ★★★ |
| **综合** | **9.3 / 10** | **9.5 / 10** |

> **两份材料合起来的转用价值，远高于各自之和**：
> A 提供"系统应该长什么样"的规格，B 提供"怎么把它卖出去并交付掉"的方法。
> 对第三家企业，最优做法是 **用 B 的叙事与节奏开场，用 A 的结构与闸门落地**。
